# The visual page builder (Arrange)

Arrange lets people build a page on the page itself: select a section in the
preview, drag it by its handle to move it, drop new sections in from a
palette of pictures, and switch a section's options — tone, alignment, which
side the picture is on — with toggles. Every action is still one small,
exact edit to the page's content file, waiting in Proof like any other
change: moving a section moves exactly its lines; adding one adds only its
lines; switching an option changes one line.

This guide is for **site developers** (what the builder needs from a site)
and ends with a short section for **editors** that the docs can lift.

---

## For site developers

### What the builder needs: two attributes

Arrange works on pages whose content has a `blocks` field — a list of
sections, each with a type (Galley detects these from your content schema or
your files; see `docs/ARCHITECTURE.md` §3.1). To arrange those sections *on
the page*, Galley has to know which element on the page is which section.

Mark each section's root element with its place in the list and its type:

```astro
{sections.map((section, index) => (
  <section data-galley-block={`sections.${index}`} data-galley-block-type={section.type}>…</section>
))}
```

- `data-galley-block` is `<blocks field key>.<index>` — `sections.0`,
  `sections.1`, … — where the key is the front-matter field that holds the
  list.
- `data-galley-block-type` is the section's type (its discriminator value).
  It lets Galley notice when the page hasn't caught up with the content yet.
- Put them on the section's **outermost** element, the one whose box is the
  section. Don't nest marked sections of the same list.

The attributes cost nothing in production; leave them in, or strip them in
your build if you prefer.

If each section is its own component, pass the marker down from the loop
and write it in one place (the `astro-saas` starter's `Sections.astro`
hands each component `block={{ key, type }}`, and `Section.astro` writes the
two attributes).

### Without the attributes

Galley tries to find the sections by **evidence**: for each section it looks
for text (headings, paragraphs, button labels) and image addresses that only
that section holds, each showing on exactly one element of the page. A
section's element is the smallest one holding all of its evidence, widened
until it would take in another section's evidence or the site's header,
footer or navigation. The mapping is used only when **every** section
resolves to its own element, none is inside another, and they appear in the
same order as in the content.

When any of that fails, Arrange is **not offered** for the page. The panel
says so plainly ("Sections can't be arranged on this page") and links here;
the form's section list keeps working, so nothing is lost. Galley never uses
a partial or "probable" mapping. Typical reasons:

- two sections show the same words (a duplicated section, two identical
  calls to action) — so duplicating a section on an unmarked site makes the
  page unmappable until its words change;
- a section shows nothing of its own (only shared images, or only text
  generated by code);
- the page renders sections out of order, nested, or interleaved.

The technical reason is under **Technical details** in the panel. Adding
the two attributes removes all of these limits.

### Thumbnails and descriptions

The palette shows each section type's label, a one-line description and a
picture. Declare them on the blocks field in `galley.config.json`:

```json
{
  "collections": [
    {
      "id": "pages",
      "fields": [
        {
          "key": "sections",
          "blocks": [
            {
              "type": "hero",
              "label": "Hero",
              "description": "The opening statement of a page: a large heading, a line of text, the main buttons.",
              "thumbnail": "galley/sections/hero.webp"
            }
          ]
        }
      ]
    }
  ]
}
```

- `thumbnail` is a **repo-relative** path to an image (WebP or PNG, about
  800 × 500, the top of the section is what shows). Keep thumbnails outside
  `public/` so they aren't deployed. Without one, the palette draws a
  plain card with the label and the section's fields.
- `description` is one sentence about when to use the section. Without one,
  the palette lists the section's fields.
- The palette lists types in the order the config gives them. It groups
  them only when the labels make groups obvious — two or more groups of
  labels that start with the same word ("Hero", "Hero with form"). There is
  no other taxonomy.

A new section starts from the most complete existing one of its type (or
the config's `example`) with its words, links and images left empty and its
settings kept.

### Options

When a section is selected, its **options** are the fields of its type that
are short, closed choices:

- `select` fields with 2–6 values (a `z.enum` in an Astro schema) become a
  segmented control — "Image side: Left · Right";
- `boolean` fields become a switch.

Free text, numbers, images and nested fields are never options; they are
edited in the form ("Edit content"). Labels come from the schema (or the
config's `label`); values are shown humanised (`media-left` → "Media left").
The value shown is the one stored, else the schema's default. Each change is
one `set` edit; a refusal from the engine puts the old value back and says
why.

### What the builder does not do

It arranges and configures **structured sections**. It does not edit
free-form layout — columns, spacing, sizes — or arbitrary HTML, and it does
not invent section types. For a new kind of section, ask the assistant in
build mode to add the component, its schema entry and a thumbnail; it then
appears in the palette.

### Forms in the preview, and chrome under a sticky header

Two rules keep the preview behaving like the site:

- **A form's buttons work as on the site.** In **Click to edit** mode a click
  on page text edits it — except on a button that belongs to a `<form>`
  (`<button>`, `<input type="submit|button|reset">`, or `role="button"`
  inside the form), where the click goes through and the form submits, as a
  visitor's would. Its words are still editable, deliberately: hover it and
  choose **Edit text** on its tag, or focus it and press ⌘Enter (Ctrl+Enter)
  — plain Enter presses it. A button outside any form is page text like any
  other, and a click edits it. (Links work the other way round — a click
  edits, **Follow link** follows — because following a link leaves the page
  you are editing, while trying a form is what the preview is for.)
- **The section label never covers the site's header.** The selected
  section's label tab and toolbar sit above its box when there is room; when
  that strip is covered by a fixed or sticky part of the page (a sticky site
  header, say) or the top of the window, they move inside the box instead.

### How it works (for the curious)

The app sends the overlay (the script the preview proxy injects) the page's
sections — type, label and evidence — and the overlay maps them to elements,
draws the chrome in a shadow root outside `<body>` (no layout shift, no
scrolling captured) and reports what the person does. The app turns each
action into an edit through the same per-entry queue the form uses (with the
entry's hash, so the form, the page and the assistant never race), and the
page shows the result when its dev server reloads. Dragging from the palette
into the page: the app keeps the pointer (frames stop taking pointer events
during the drag), sends the pointer's position in the frame's coordinates,
and the overlay — which knows where the sections are — draws the drop line,
scrolls near the edges and names the gap. The protocol is
`OverlayToHost` / `HostToOverlay` in `packages/core/src/types.ts`
(`arrange`, `arrange-status`, `arrange-select`, `arrange-action`,
`placing`, `placing-pointer`, `placing-drop`, `placing-at`, `place`).

## For editors: arranging a page

1. Open the page and choose **Arrange** above the preview.
2. **Select** a section by clicking it. Its toolbar appears: drag handle,
   move up, move down, duplicate, remove, **Options** and **Edit content**.
3. **Move** a section by dragging its handle. The page makes room and a line
   shows where it will land; near the top or bottom the page scrolls. Press
   Escape to leave it where it was.
4. **Add** a section from the panel beside the page: drag its picture onto
   the page, or click it and then press a **＋** line between sections (or
   **Add at the end**). You can also press a ＋ between two sections first and
   then pick what goes there.
5. **Options** — tone, alignment, picture side — are toggles in the panel.
   The page updates a moment after each change.
6. **Edit content** opens the section's fields in the form.
7. Removed something by mistake? Every move, duplicate and removal offers
   **Undo**, which puts the page back exactly as it was.

From the keyboard: Tab to the page's sections, ↑ and ↓ to choose one,
Alt+↑ / Alt+↓ to move it, Delete to remove it, Enter to edit its content,
Tab again for its toolbar, and ⌘Z (Ctrl+Z) to undo. Nothing goes live until
you publish; every change is waiting in Proof.

If the panel says **Sections can't be arranged on this page**, the site
hasn't marked its sections for the page builder. Add, move and remove them
in the form instead, and ask the site's developer to add the markers (above).
