# Desktop app

A thin native shell around the same server and web UI the CLI runs. It starts
the server privately on 127.0.0.1, shows its UI in a native window, adds what
a browser tab can't (a folder picker, Finder, a menu, links that open in your
browser), and stops everything when you quit. Tauri 2, Rust, the system
webview (WebKit on macOS) — no bundled Chromium.

```
apps/desktop/
├── package.json                  @galley/desktop: dev, bundle, prepare-sidecar, icons, tests
├── ui/                           the start-up window (plain HTML/CSS/JS, brand token values)
├── scripts/
│   ├── prepare-sidecar.mjs       builds what the packaged app runs (tauri build runs it first)
│   ├── sidecar-e2e.mjs           end-to-end check of a server runtime (how the sidecar was chosen)
│   ├── shutdown-e2e.mjs          launches the real app; proves both shutdown paths
│   └── render-icon.mjs           brand/logo/app-icon.svg → 1024 px PNG for `tauri icon`
└── src-tauri/
    ├── tauri.conf.json           product name, identifier, window-less start, CSP, bundle
    ├── tauri.bundle.conf.json    merged in by `bundle`: sidecar, server resources, prepare step
    ├── capabilities/             the start-up window's permissions (the main window's are granted at run time)
    ├── permissions/autogenerated generated by tauri-build from the command list in build.rs
    ├── entitlements.plist        hardened-runtime exceptions the bundled Node needs (JIT)
    ├── build.rs                  command list + brand.rs generated from packages/core/src/brand.ts
    ├── icons/                    generated from the brand icon (committed)
    └── src/
        ├── shell.rs              lifecycle: windows, start, retry, watch, quit
        ├── server.rs             locate, spawn, wait for /api/meta, stop (TERM → 5 s → KILL)
        ├── procs.rs              process groups and the process tree (orphaned dev servers)
        ├── env_path.rs           the login shell's PATH + common install folders
        ├── preflight.rs          is git / Node.js installed?
        ├── bridge.rs, bridge.js  window.__GALLEY_DESKTOP__ and its commands
        ├── nav.rs                navigation allow-list, argument validation
        ├── menu.rs               the native menu (File › New window, Open recent…; the Window list)
        ├── windows.rs            app windows: main, one per site, plain; remembered site windows; folders opened from outside
        ├── dock.rs               macOS: the Dock menu of recent sites
        ├── http.rs, net.rs       loopback HTTP client; port and token
        ├── signals.rs            SIGTERM/SIGINT/SIGHUP → a normal quit
        └── selftest.rs/.js       debug builds only: in-page checks for shutdown-e2e
```

## Prerequisites

- Rust stable 1.90 or later (`rustup`), and the platform's build tools: Xcode
  command-line tools on macOS; MSVC build tools and WebView2 (preinstalled on
  Windows 11) on Windows; on Debian/Ubuntu
  `libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev`.
- Node.js 20.11 or later and pnpm 10 (the repository's own requirements).
- The Tauri CLI comes from npm as a dev dependency (`@tauri-apps/cli`); nothing
  to install globally.

## Develop

```sh
pnpm install
pnpm --filter @galley/desktop dev
```

`tauri dev` builds the shell in debug and starts it. A debug build runs the
monorepo's CLI with your own Node (`node packages/cli/bin/galley.js desktop …`),
so changes to the server or the engine need only a restart of the app, and no
bundling step. The web UI it shows is `packages/web/dist`; build it with
`pnpm --filter @galley/web build` (or watch it) — until then the server shows
its "UI not built" page. Debug builds print `[desktop]` and `[server]` lines
on stderr.

`packages/cli/bin/galley.js` prefers `packages/cli/dist/galley.mjs` when it
exists, so a leftover CLI bundle would be what a debug build runs.
`prepare-sidecar` removes the bundle again when it built one that wasn't
there before.

The app keeps its state in the same home as the CLI (`~/.galley`, or
`GALLEY_HOME` when set in the environment it was started from), so both see
the same sites and settings.

## Lifecycle

1. **Start-up window** (`ui/index.html`, a local page): the brand mark and
   "Starting…".
2. **PATH.** An app opened from the Finder gets launchd's PATH
   (`/usr/bin:/bin:/usr/sbin:/sbin`), which wouldn't find git, node, npm or
   pnpm from Homebrew, nvm, Volta, fnm… The shell runs
   `$SHELL -ilc 'printf … "$PATH" …'` (5 s timeout, killed as a process group
   if it hangs; fish handled), then appends the common install folders that
   exist (`/opt/homebrew/bin`, `/usr/local/bin`, `~/.volta/bin`,
   `~/.nvm/versions/node/*/bin` newest first, fnm, asdf, mise, `~/.local/bin`,
   `~/.bun/bin`, pnpm's home…). The server and everything it runs get that PATH.
3. **Pre-flight.** `git --version` and `node --version` must answer. If not,
   the start-up window says which is missing, what it is for and where to get
   it, with **Check again** (re-reads PATH) and **Continue without them**.
4. **Server.** A free loopback port (the last one used when it is still free,
   so the UI keeps the same origin and its browser storage between launches),
   a fresh 256-bit token, and the server started as
   `<runtime> <cli> desktop --exit-with-parent --port <port>` with
   `GALLEY_DESKTOP=1 GALLEY_HOST=127.0.0.1 GALLEY_PORT GALLEY_TOKEN`, in its
   own process group, stdin a pipe the shell holds and never writes. No site
   argument: the UI opens on the sites list.
5. **Ready** when `GET /api/meta` (Bearer token) answers with `desktop: true`,
   polled every 150 ms. Then the main window opens at
   `http://127.0.0.1:<port>/?token=<token>` (the server swaps the token for an
   HttpOnly cookie and drops it from the address) and the start-up window
   closes.
6. **Failure.** If the server exits early or doesn't answer within 30 s, the
   start-up window shows "Couldn't start" with **Try again** and **Quit**, and
   the exit status and last 40 lines of output under Technical details. If the
   server stops later, the main window closes and the same window says it
   stopped. There is never a blank window.

**Quitting.** Closing the last window quits the app — on macOS too. The
window *is* the app here: a windowless app would keep the server and any
preview running with nothing to show for it, and reopening from the Dock would
mean starting everything again anyway. Quit (⌘Q), closing the last window,
logging out, `kill <pid>` and Ctrl+C in a terminal all take the same path:
SIGTERM to the server's process group, up to 5 s for it to stop its previews
and close, then SIGKILL. Before signalling, the shell notes the server's
process tree; a dev server that outlives a killed server (the engine runs each
in a session of its own, out of reach of the group signal) is killed too.

**When the shell can't clean up** (it crashed, or was `kill -9`ed), the
operating system closes the server's stdin. `galley desktop --exit-with-parent`
treats end-of-file there as "my parent is gone", closes the server (which
stops its previews) and exits; if closing hangs, it exits anyway after 8 s,
and its exit hook kills any dev server still running.

**Single instance.** A second launch focuses the running app's window
(`tauri-plugin-single-instance`); a folder or a `galley://open?path=…` link
given to it is opened by the running app (below). **Window size and position**
are remembered (`tauri-plugin-window-state`, per window label; the start-up
window is excluded). Minimum window size 1024 × 680.

## Windows

- **One window per site.** The web UI asks for one with
  `window.open("/sites/<id>…?galley-window=new")` (a site's menu on the Sites
  screen, ⌘-Enter in the switcher, ⌘-click on a site's name). `on_new_window`
  turns that — and only that: the app's own origin, a `/sites/<id>` path with
  a well-formed id, the flag — into a window labelled `site-<id>`
  (`nav::site_window_request`); asking again focuses it. Every other
  `window.open` still goes to the browser. The window is titled with the
  site's name.
- **File › New window** opens another window on the Sites screen
  (`window-<n>`); **File › Open site in new window…** picks a folder and opens
  it in a site window; **File › Open recent** lists the most recently opened
  sites (from `GET /api/sites`), with **Clear**; **File › Add sites from a
  folder…** opens that flow on the Sites screen.
- **The Window menu** lists open windows (macOS does this itself; elsewhere
  the shell adds them). **The Dock menu** (macOS) lists recent sites: Tauri has
  no API for it, so `dock.rs` gives the app delegate an
  `applicationDockMenu:` returning a muda menu, whose clicks arrive in
  `menu::handle` like any other item.
- **Remembered across launches.** Which site windows were open is kept in
  `windows.json` in the app's config folder (a window the person closes is
  dropped from it; quitting keeps them all), and they reopen after the main
  window. Menu, recent list and Dock menu are rebuilt a moment after windows
  open or close and pages load.
- **Opening a folder from outside.** A folder dropped on the Dock icon and
  `galley://open?path=…` links arrive as `RunEvent::Opened` (macOS; the
  bundle's `Info.plist` registers the scheme and folders as a document type);
  elsewhere, and for a second launch, as arguments. Each is checked for shape
  in Rust (`nav::open_request`: an absolute, plain path to an existing
  folder), then sent to `POST /api/sites/open` — exactly what the folder
  picker's choice goes through — and only a site the server accepted gets a
  window. Requests that arrive before the server is up wait for it.
- **Closing the last window quits**, as before; closing the main window while
  a site window is open doesn't.

## How the server is bundled (and why Node)

`pnpm --filter galley-cms build` produces `packages/cli/dist/galley.mjs` (one
ESM file: CLI, server, engine) with `web/`, `starters/` and `overlay.js` beside
it. The packaged app needs a JavaScript runtime for it that the person doesn't
have to install.

**Tried first: `bun build --compile`** (Bun 1.1.17, the version on the build
machine) into one 57 MB executable. `scripts/sidecar-e2e.mjs` runs the real
flow against a runtime — start with `--exit-with-parent`, open a git-initialised
copy of `starters/astro-starter` (`node_modules` symlinked), list, read, edit,
proof, publish, see an outside edit in a nested folder arrive on
`/api/events`, start the preview (the site's own dev server), fetch HTML
through the preview proxy with the overlay injected, upgrade a WebSocket
through the proxy and receive Vite's HMR greeting, then close stdin and check
the server, proxy and dev server have all gone. Under Bun it failed at the
first step: the binary bound its port, but every request ended in
`error: Expected a Response object, but received 'Response (lightweight) {…}'`
(212 times in one run) — `@hono/node-server` replaces the global `Response`
with its own lightweight class, which Bun's `node:http` rejects — so nothing
after start-up could even be attempted.

**What ships: a real Node.js runtime as the sidecar.** `prepare-sidecar.mjs`
copies the Node executable that runs it (or `GALLEY_NODE_BINARY`) to
`src-tauri/binaries/<slug>-node-<target triple>` (`externalBin`; Tauri installs
it next to the app's executable without the suffix) and the CLI bundle to
`src-tauri/resources/server/` (installed as `Resources/server/`), with Node's
licence as `NODE-LICENSE.txt` (Node.js is MIT-licensed; the file includes the
licences of the components it bundles). The same e2e script passes all ten
steps with exactly that runtime and bundle. A release build of the shell finds
both and runs `<exe dir>/<slug>-node <resources>/server/<slug>.mjs desktop …`;
a debug build without them runs the monorepo's CLI instead.

The cost is size: Node is ~120 MB uncompressed (the Bun binary would have been
57 MB). CI bundles Node 22 (LTS); a local `bundle` uses whatever Node runs it
and warns when that isn't an LTS release.

## Security model

The UI comes from `http://127.0.0.1:<port>`, which Tauri treats as a remote
origin. Remote origins get no IPC at all unless a capability names them, and
because the app lists its commands in `build.rs` (`AppManifest::commands`),
even its own commands need a permission.

**Every app window's page** — the main one, each site's, each plain extra
one — may call exactly three commands. A capability is added at run time for
each window label, just before that window is built, once the port is known,
so it names that port and that window only (a label never granted has no
commands at all):

```rust
CapabilityBuilder::new(format!("app-origin-{port}-{label}"))
    .remote(format!("http://127.0.0.1:{port}/*"))
    .local(false)
    .window(label)
    .permission("allow-pick-folder")
    .permission("allow-open-external")
    .permission("allow-reveal-in-finder")
```

No plugin permission is granted to any window: the dialog and opener plugins
are used from Rust only. Tauri checks the calling frame's `Origin` on every
call, so a preview iframe (another loopback port) can't call these commands
either. On macOS the IPC script isn't injected into iframes at all (checked:
`window.__TAURI_INTERNALS__` is undefined in a preview-like frame).

**The start-up window** (a local page) has `capabilities/startup-window.json`:

```json
{
  "identifier": "startup-window",
  "local": true,
  "windows": ["startup"],
  "permissions": ["allow-startup-state", "allow-startup-retry", "allow-startup-continue", "allow-startup-quit", "allow-open-external"]
}
```

**Arguments are checked in Rust**, whatever the page sends:
`openExternal(url)` — http/https only, with a host, no credentials, at most
8 KB; `revealInFinder(path)` — absolute, no `.`/`..` segments, then only if it
is (after resolving links) the root of a site the server lists in
`GET /api/sites`; `pickFolder()` takes nothing.

**`window.__GALLEY_DESKTOP__`** is defined by an initialization script in the
main window's top frame only, and only when the page's origin is the app's:

```ts
interface DesktopBridge {
  readonly version: string;
  pickFolder(): Promise<string | null>;
  openExternal(url: string): Promise<void>;
  revealInFinder(path: string): Promise<void>;
}
```

It is frozen and non-writable.

**Navigation is locked to the app's origin** so the window that holds those
permissions can't be turned into a browser for someone else's page, and so
links behave as people expect (they open in their browser). In three layers:

1. `on_navigation` (every frame) lets web pages, `about:blank`/`srcdoc`,
   `blob:` and `data:` load, and refuses `file:`, custom schemes and the rest.
   On macOS this hook fires for iframes too and can't tell them from the top
   frame, so it can't be stricter without breaking the preview and whatever
   the previewed site embeds (a video, a map).
2. The bridge script sends clicks on links that leave the app to the default
   browser; `window.open` and `target="_blank"` go through `on_new_window`,
   which always opens outside and never creates a window.
3. Page-load events are top-frame only: if the top-level page still lands
   somewhere else, the shell opens that address in the browser and takes the
   window back to the app.

**Preview iframes** on other loopback ports load normally: the server's own
CSP for the UI allows `frame-src http://127.0.0.1:* http://localhost:* http://[::1]:*`,
and nothing in the shell's configuration blocks them (checked in the real
webview by `test:shutdown`). Tauri's `app.security.csp` in `tauri.conf.json`
applies only to the start-up window's bundled page.

## Build installers

```sh
pnpm --filter @galley/desktop bundle            # all formats for this OS
pnpm --filter @galley/desktop exec tauri build --bundles app --config src-tauri/tauri.bundle.conf.json
```

`bundle` merges `tauri.bundle.conf.json` (sidecar, resources, and
`beforeBuildCommand: node scripts/prepare-sidecar.mjs`). `prepare-sidecar`
builds the web UI and the CLI bundle, copies them and the Node runtime into
place, and refuses to continue if the web UI is missing or the Node binary
doesn't match the target. Set `GALLEY_SKIP_WEB_BUILD=1` to use
`packages/web/dist` as it is. Output: `src-tauri/target/release/bundle/`.

CI (`.github/workflows/desktop.yml`) builds macOS (Apple silicon and Intel),
Windows and Linux on version tags and by hand. After each build it starts the
packaged server the way the app does and walks a site through it
(`scripts/sidecar-e2e.mjs`), so an installer whose server can't run fails
there. The macOS builds are signed with a Developer ID and notarised by
Apple, and the job checks the result (`codesign`, `stapler`, `spctl`); the
signing steps run only when their secrets exist, and the workflow's header
lists them. On a version tag the installers and their SHA-256 sums go into a
draft release for a person to publish.

## Tests

```sh
pnpm --filter @galley/desktop test:rust       # unit tests: PATH, ports, tokens, HTTP, process tree, URL/argument checks, brand
pnpm --filter @galley/desktop test:sidecar    # the end-to-end flow against the dev runtime
pnpm --filter @galley/desktop test:shutdown   # launches the real debug app twice (quit, kill -9); macOS
```

`test:shutdown` starts the app with a Finder-like PATH and a temporary
`GALLEY_HOME`, checks the server answers with `desktop: true`, finds the main
window in the window list, runs the in-page self-test (bridge, refused
arguments, refused commands, a loopback iframe), opens a site, launches the
app a second time with the site's folder (the running app opens it in a
window of its own), checks both windows are in the window list and that the
site's window ran the same self-test with exactly the same bridge, starts a
real preview, then quits — once with SIGTERM, once with `kill -9` — and
checks no port is listening and no process from the app's tree is left. The
second round also checks the site's window was reopened at launch. Each
window writes its self-test to `GALLEY_DESKTOP_SELFTEST_OUT` (main) or
`<that>.<label>`. It isn't part of
`pnpm test`: it needs a desktop session and a built app.

## Icons

```sh
PLAYWRIGHT_CORE_FROM=/path/to/node_modules pnpm --filter @galley/desktop icons
```

Renders `brand/logo/app-icon.svg` to `src-tauri/icons/source/app-icon-1024.png`
with an already-installed headless Chromium (playwright-core; it never
downloads a browser), then `tauri icon` writes the set. The generated icons
are committed.

## Not done yet

- **Auto-update.** No updater; new versions are installed by hand.
- **Code signing on Windows and Linux.** macOS is signed and notarised. The
  Windows installers are unsigned and trigger SmartScreen (More info › Run
  anyway); CI signs them through Azure Artifact Signing once its secrets are set
  (the workflow's header lists them); until a run has, that step is unproven.
- **Windows and Linux in a person's hands.** Both are built in CI, their Rust
  tests pass, and the packaged server opens, edits, proofs, publishes and
  previews a site there. On Windows CI also installs the app from its
  installer, opens it and keeps a picture of the window (it shows the Sites
  screen). Beyond that the shell — the menu, the folder picker, process-tree
  kill with `taskkill /T`, the `ps`-based orphan sweep on Linux — has only
  been used by a person on macOS, and on Linux the window has never been
  opened.
- **The OS keychain for secrets** (ARCHITECTURE.md §6) isn't wired yet; keys
  are still kept by the engine in the Galley home.
- **The "closing the last window quits" path** is implemented by Tauri's
  default and wasn't driven by a test here (it needs UI automation
  permission); quitting by signal was.
